# Writing a migration

The schema lives in the model and migrations are generated by diffing it:

```powershell
dotnet dotnet-ef migrations add <Name> --project src/MeetingTranscriber.Infrastructure
```

Everything below is a way that command goes wrong. Two of the five fail silently and one blames
something that is not at fault, which is why they are written down rather than learned twice.

## Check the id sorts last, before anything else

A migration runs in the position its id sorts to, so an id that lands before one already committed
runs in the wrong order — and every check below is meaningless against a migration you tested in a
position it will never run in. `ls` the folder and confirm the new file is last.

Twelve of the ids here are hand-picked and were ahead of the clock at the time, which is why a
generated one used to sort before them and had to be renamed into the next free slot. That block
ends at `20260806200000_Affiliations`; the clock passed it on 2026-08-07, so a generated timestamp
now sorts last on its own and is kept. Renaming one into an invented slot from here would be
reintroducing hand-picked ids for a problem that no longer exists.

## Run `dotnet format` afterwards

What EF scaffolds does not satisfy `dotnet format`, so run it before committing or CI fails on code
nobody wrote.

## A composite foreign key onto a new UNIQUE constraint takes two migrations

SQLite rebuilds the whole table for almost any schema change, and a composite foreign key onto a
UNIQUE constraint that the same rebuild is adding cannot resolve: the new table references the old
one by name, and the old one has no such key yet. `nodes` pointing at its own parent is exactly
that, and it fails with `foreign key mismatch`.

Split it: the columns and the unique constraints in one migration, the foreign key in the next.
`20260806190000_TreeColumnsAndRunState` and `20260806191000_TreeKeys` are the pair that had to.

## FTS5 tables and triggers are invisible to the model

EF models tables, not FTS5 virtual tables or triggers. Those are hand written in their own
migration and never appear in the model snapshot, so renaming an indexed column generates a
migration for the table and silently leaves the triggers pointing at a column that no longer
exists. Check them by hand — the snapshot will not.

## `dotnet-ef` blocked by Smart App Control

`dotnet-ef` loads the freshly built assembly into its own process, so Smart App Control blocks it
outright: `Could not load assembly`, wrapping `An Application Control policy has blocked this file`
(0x800711C7). It reads like an EF bug and is not one, and `dotnet build` and `dotnet test` are
unaffected, which is what makes it confusing.

```powershell
Get-WinEvent -LogName Microsoft-Windows-CodeIntegrity/Operational   # names the blocked file
(Get-ItemProperty HKLM:\SYSTEM\CurrentControlSet\Control\CI\Policy).VerifiedAndReputablePolicyState
```

The fix is to turn Smart App Control off. Failing that, a migration, its designer and the model
snapshot can be written by hand: `HasPendingModelChanges` in `CorpusMigrationTests` is what proves
they match, so a hand-written one that passes it is as good as a generated one.
